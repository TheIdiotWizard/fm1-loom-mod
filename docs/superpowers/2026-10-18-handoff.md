What got there (in order): events within 8 samples fire together (stretches 1.4 -> 1.1 a block); a note's set-up in
its render; the effects' job starts on core 2 with the block, beside the sequencer, and core 0 hands core 2 voices
when it frees; the split by each voice's measured cost (FM-1 only; the host keeps the model); three engine passes
(brocade, voile/cane, weft/stack/tines: 7-21 % each on the FM-1); a stereo voice's filter a channel at a time (-6 KB);
voices rendered grouped by engine. USB recordings: fm1-base's USB audio ring a half deeper (FM1B_UAC_DEEP; merged
and pushed with main) - the "breakups" in a USB recording were the ring running dry, not dropouts.

The biggest cost left is the **flash cache** (written up on its own: `2026-10-18-flash-cache.md`): code runs from the flash through the XIP cache, and in a song each
voice's engine evicts the others'. Alone a weft voice adds ~2.5 % of a block (measure_load.sh); in a song ~11 %
(the profiler's slowest-block voices: perf_read.py vblk_text). Next step: a bigger RAM code area. It is fm1-base's
choice, not the chip's: base/device/app.ld gives RAMTEXT 24 KB (17.6 KB used: the effects, the master, core 2's loop),
an 8 KB gap "for RAM-run debug", RAM 96 KB, POOL 336 KB (11.6 KB free). Taking the gap and part of the pool would
let the hot voice code run from RAM: flt_loop / sample_loop / out_loop and the busiest engines' loops (eng_run is
23 KB for all engines; voice_chunk 20 KB, per chunk). Needs: app.ld, the PC guard's window, tools/size_fns.py's
RAM placement (RAM code cannot call the flash directly: the set must be closed, see RAM_DSP / RAM_INLINE).

"Never peak" needs a budget, not only speed: the overload guard averages over blocks and never trips on a one-block
chord spike. Plan: at note-on, predict the block's cost from the measured voice costs (+ drums, effects, master); over
~90 % give up a quiet releasing voice, then the track's oldest, last the new note. Ask the user what gives way first.
